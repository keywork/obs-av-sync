# Plan 05-03: Settings persistence + lifecycle handling

## Objective
Complete the end-to-end lifecycle for per-filter configuration:
1. **Persistence** — `reference_source_name` and `sync_enabled` are saved to and loaded from the OBS scene collection automatically via `obs_data_t`.
2. **Source removal safety** — If the designated reference source is deleted from OBS while the tap is active, the plugin logs a warning, detaches the audio callback, and leaves the per-filter state intact (holding the last known offset). No crash.
3. **Enable/disable runtime behaviour** — When `sync_enabled` is `false`, the filter continues to downmix and write to its per-source ring (zero warm-up on re-enable) but must not apply sync offsets. For Phase 5, this means guarding any `obs_source_set_sync_offset` calls; since the analysis thread does not yet exist, the guard is placed on the conceptual path and on the audio callback's reference-tap interaction.
4. **Cleanup** — Filter destroy releases the `reference_source_name` string.

## Background
OBS persists filter settings automatically: it calls `obs_data_set_*` internally when the scene collection is saved, and passes the saved `obs_data_t` back to `av_sync_filter_create` on load. The plugin only needs to read the keys in `create`/`update` and write them back implicitly via `obs_data_set_*` if manual updates are needed (they are not — OBS tracks property changes itself).

The source-removal safety requirement (D-03) means the reference tap must survive the disappearance of its source. The simplest robust approach is to add a small helper inside `reference_tap_set_source` that checks whether `ref_source` is still valid before any operation that touches it. Because OBS does not provide a direct "is this source pointer still alive" API, we rely on the following: when a source is removed, OBS calls `obs_source_remove_audio_capture_callback` automatically if the source is being destroyed (the callback list is cleaned up). Our `reference_tap_shutdown` also explicitly removes the callback. The gap — a source removed while the plugin is still running — is handled by having `reference_tap_set_source` called with a new name (or NULL) whenever the user changes the reference, and by logging a warning if `obs_get_source_by_name` returns NULL at startup.
