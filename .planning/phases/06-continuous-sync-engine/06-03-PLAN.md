# Plan 06-03: Drift tracking + lifecycle hardening

## Objective
Harden the continuous sync engine for real-world production conditions: expose an atomic status field for the Phase 8 dock UI, emit diagnostic logs at 5-second intervals and on status transitions, guard against sample-rate mismatches between reference and per-filter sources, detect per-filter source stream restarts and reset consumer cursors, and add a `reference_tap_get_sample_rate()` accessor. Finally, verify by inspection that all four Phase 6 success criteria from ROADMAP.md are satisfied by the design parameters (EMA α=0.3, 2 Hz rate, 4-second window, slew-rate cap).

## Background
D-15 and D-16 state that the EMA naturally tracks slow drift with no periodic reset. The smoother's time constant (~3 updates at α=0.3 ≈ 1.5 seconds) is fast enough for typical IP camera drift. D-20 and D-21 require holding the last offset when the reference is removed or the source is muted; this is already achieved by the smoother state persisting in `data` while the thread skips iterations. This plan adds visibility (logging, status) and safety (rate matching, restart detection) around that core behaviour.

```c
		}
```

The status field is `_Atomic int` and is updated with relaxed ordering because it is a simple indicator polled by the UI thread; exact synchrony is not required.

```c

		av_sync_ring_get_stats(data->ring, &src_stats);
		if (src_stats.total_written < data->last_src_total_written) {
			obs_source_t *parent = data->source ? obs_filter_get_parent(data->source) : NULL;
			const char *parent_name = parent ? obs_source_get_name(parent) : "(unknown)";
			obs_log(LOG_WARNING,
				"analysis thread on '%s': source stream restarted; resetting cursor",

		}
		data->last_src_total_written = src_stats.total_written;
```

This detects a decreasing `total_written` (which would only happen if the ring were recreated or reset) and re-initializes the consumer cursor so the next read starts from the oldest valid sample.

Document the verification argument in the code comments and confirm by inspection that each success criterion is met:

1. **Auto-correct within 10 seconds** — At 2 Hz (500 ms sleep) with a 4-second window, the first valid measurement can occur as soon as 4 seconds of audio are buffered. The EMA with α=0.3 converges in ~3 updates (~1.5 seconds) after the first accepted sample. Total expected convergence: 4 + 1.5 = 5.5 seconds, well under 10 seconds. Add a comment in `av_sync_analysis_thread`:

```c
/* Success criterion 1: 2 Hz rate + 4 s window + EMA α=0.3 → convergence
   within ~6 s of stream start, satisfying the ≤10 s requirement. */
```

2. **Residual < 20 ms during 60-minute session** — The slew-rate cap limits each update to ±20 ms. Once synced, the EMA smooths jitter; the cap prevents any single bad measurement from creating a large jump. The 4-second GCC-PHAT window provides strong correlation at ≥10 dB SNR, giving accurate raw estimates. Add a comment:

```c
/* Success criterion 2: 20 ms slew-rate cap + EMA smoothing keeps residual
   below 20 ms once converged, even during long sessions. */
```

3. **Mute reference for 10 s → hold last offset** — When the reference is muted, `reference_tap_get_ring()` may return a ring that stops receiving data, or the ring may simply stop growing. The analysis thread detects `ref_read < n` and skips the iteration without resetting smoother state. The last `smoothed_offset_ms` remains in `data` and continues to be applied (if already applied) because `obs_source_set_sync_offset` is not called again. Add a comment:

```c
/* Success criterion 3: insufficient data → skip iteration; smoother state
   and applied offset are held, not reset. */
```

4. **300 ms offset → ≤20 ms within 30 seconds** — With α=0.3, each accepted update closes ~30% of the remaining gap. Starting from 300 ms:
   - Update 1: 300 → 210 ms (gap closed 90 ms)
   - Update 2: 210 → 147 ms
   - Update 3: 147 → 103 ms
   - Update 4: 103 → 72 ms
   - Update 5: 72 → 50 ms
   - Update 6: 50 → 35 ms
   - Update 7: 35 → 25 ms
   - Update 8: 25 → 18 ms (≤20 ms reached)
   At 2 Hz, 8 updates = 4 seconds. The slew-rate cap of 20 ms per update would slow this slightly: 300 ms / 20 ms = 15 updates max = 7.5 seconds. Either way, well under 30 seconds. Add a comment:

```c
/* Success criterion 4: EMA α=0.3 converges from 300 ms to ≤20 ms in ~8
   updates (~4 s). Slew-rate cap worst case: 15 updates (~7.5 s). Both
   satisfy the ≤30 s requirement. */
```

Place these four comments together near the top of `av_sync_analysis_thread`, immediately after the cursor initializations.
