# Plan 07-01: Research ONVIF Clock-Sync Feasibility

## Objective
Review the ONVIF Device Management specification, evaluate NTP/PTP/`GetSystemDateAndTime` as clock-sync mechanisms for IP cameras, survey ONVIF client libraries for license compatibility, and document accuracy floors and integration feasibility. Output feeds into `07-RESEARCH.md`.

## Context & Decisions
| Decision | Rationale | Source |
|----------|-----------|--------|
| Evaluate all three clock-sync mechanisms (NTP, PTP, GetSystemDateAndTime) | Each has different accuracy floors and camera support levels; need comparison for recommendation | `07-CONTEXT.md` D-03, D-04 |
| Adoption threshold ≤ 5 ms | Below GCC-PHAT live residual (≤ 20 ms) to justify integration cost | `07-CONTEXT.md` D-11, ROADMAP.md Phase 7 success criteria |
| Document-first, prototype-gated | Phase 7 deliverable is a recommendation doc; code only if spec review shows clear promise | `07-CONTEXT.md` D-05, D-06 |
| Generic ONVIF Profile S/G cameras | Plugin targets arbitrary IP cameras, not just current production models | `07-CONTEXT.md` D-07, D-08 |

<action>
Research and document:
1. SOAP over HTTP round-trip time (RTT) behavior for `GetSystemDateAndTime` on a typical LAN — cite measured or documented RTT ranges

3. Jitter in RTT measurements and its effect on repeated clock-delta sampling

### Task 6: Document integration path feasibility (direct vs. external)
<read_first>
- `.planning/phases/07-onvif-drift-evaluation/07-CONTEXT.md` (decisions D-09, D-10)
- `.planning/phases/07-onvif-drift-evaluation/07-RESEARCH.md` (after Task 5)
- `src/av_sync_filter.c` (to observe pthread usage pattern for background threads)
- `docs/ARCHITECTURE.md` (threading model section)
</read_first>

<action>
Document the feasibility of two integration paths:

**Path 1: Direct ONVIF from plugin**
- OBS plugins can spawn background pthreads (verified by `av_sync_filter.c` analysis thread)
- Assess whether blocking TCP connect/send/recv on a dedicated background thread is safe inside OBS
- Document any OBS API restrictions on outbound network I/O from plugins
- Note XML/SOAP parsing CPU cost and memory footprint on a background thread

**Path 2: External tool / helper process**
- Describe how a standalone utility would query cameras and communicate results to the plugin
- Evaluate IPC options: file polling (simple, high latency), named pipe (Windows/macOS/Linux differences), localhost UDP/TCP socket (port management), shared memory (complex, platform-specific)
- Estimate end-to-end latency for each IPC option
- Document operational complexity (user must run a second process? auto-launched by OBS?)

State the preferred path and the specific technical blockers for the non-preferred path.
</action>

<acceptance_criteria>
- `07-RESEARCH.md` contains a section `## Integration Path Feasibility`
- Both "Direct" and "External" paths are described with at least two bullet points each
- A preferred path is explicitly stated with a one-sentence rationale
- Specific technical blockers for the non-preferred path are listed as bullet points
</acceptance_criteria>
