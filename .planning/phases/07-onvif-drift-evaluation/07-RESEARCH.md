## 1. ONVIF Device Management Clock Primitives

**Source:** `ONVIF Core Specification v22.12`, §8.3.6 (GetSystemDateAndTime), §8.3.7 (SetSystemDateAndTime), §8.8 (Network — NTP)
**Source:** `daihn/onvif/devicemgmt.wsdl` — `GetSystemDateAndTimeResponse` complexType

The ONVIF Device Management Service (`http://onvif_host/onvif/device_service`) is the mandatory entry point for all ONVIF devices. The specification defines four clock-relevant operations:

### 1.1 `GetSystemDateAndTime`
- **Mandatory** per ONVIF Core Specification §5.1.2: "An ONVIF compliant device shall provide the device management and event service."
- **Does not require authentication** per ONVIF Application Programmer's Guide §5.1.3 — it is the standard reachability probe.
- **Request:** empty body.
- **Response structure (`SystemDateAndTime` type):**
  - `DateTimeType` — enum `Manual` or `NTP`; indicates how the device maintains its clock.
  - `DaylightSavings` — boolean.
  - `TimeZone` — `tt:TimeZone` with `TZ` token in POSIX 1003.1 format (e.g., `UTC-05:00`).
  - `UTCDateTime` — `tt:DateTime` (`Date` + `Time`) in UTC. The spec states: "A device shall provide the UTCDateTime information."
  - `LocalDateTime` — same structure, camera-local time.
- **Timestamp nature:** The returned `UTCDateTime` is the camera's current estimate of UTC at the moment the response is assembled. It is **not** a hardware-timestamped network event; it is generated by the camera's OS/firmware and subject to the camera's own clock discipline (NTP client, manual setting, or free-running RTC).

### 1.2 `SetSystemDateAndTime`
- **Optional** — not all devices allow external time setting.
- **Request fields:** `DateTimeType`, `DaylightSavings`, `TimeZone`, `UTCDateTime`.
- If `DateTimeType` is `NTP`, the `UTCDateTime` field "has no meaning" per WSDL annotation; the camera is expected to use its configured NTP servers.

### 1.3 NTP Configuration (`GetNTP` / `SetNTP`)
- **Optional** per Device Management service.
- Returns `NTPInformation` containing a list of `NetworkHost` entries (type `IPv4`, `IPv6`, or `DNS`).
- Allows reading or setting the camera's NTP server list. This is a **configuration** primitive, not a **measurement** primitive — it does not expose sync status (stratum, offset, jitter) on most generic cameras.

### 1.4 PTP / IEEE 1588
- **Not defined** in the ONVIF Device Management Service WSDL or Core Specification.
- ONVIF does not standardize PTP configuration, status queries, or clock control. PTP support (where present) is a **camera-side Ethernet NIC feature** exposed through vendor-specific APIs or GigE Vision registers, not through ONVIF SOAP.

**Key Insight:** The only mandatory, universally available clock primitive across all ONVIF devices is `GetSystemDateAndTime`. It returns the camera's current UTC estimate, but the spec makes no accuracy claims about how that time is derived or how fresh it is.

## 2. NTP Accuracy Evaluation

**Source:** RFC 5905 (NTPv4), §Overview — "Typical secondary servers and clients on fast LANs are within a few hundred microseconds with poll intervals up to 1024 seconds ... servers and clients are precise within a few tens of milliseconds with poll intervals up to 36 hours."
**Source:** NIST Technical Report "Practical Limitations of NTP Time Transfer" (Novick & Lombardi) — measured NTP over dedicated LAN at < 10 µs (1σ) for direct crossover, < 15 µs for single-hop switch, ~20 µs for two-hop routed LAN.
**Source:** Edgertronic Wiki — "If the NTP server is located on the same local area network (subLAN), and several cameras are used, the difference in time of the Linux wall clocks in the cameras should be maximum of a few milliseconds."
**Source:** IPVM Public Report on Network Time Sync — documents that NTP sync to *different* servers can produce 1–3 s discrepancies; syncing all cameras to the *same* server eliminates this.

### 2.1 Accuracy Floor on IP Cameras
| Scenario                                    | Expected Accuracy | Notes                                                                |
| ------------------------------------------- | ----------------- | -------------------------------------------------------------------- |
| Dedicated LAN, local NTP server, tuned NICs | 0.1–1 ms          | NIST measurements with GPS-rubidium server and optimized client      |
| Typical gigabit LAN, unmanaged switch       | 1–5 ms            | Common for general-purpose OS NTP clients                            |
| Consumer/prosumer IP camera firmware NTP    | 1–10 ms           | Camera SoCs run lightweight embedded NTP clients with coarse polling |
| WAN / Internet NTP                          | 10–100+ ms        | Asymmetry dominates; irrelevant for live production                  |

**Realistic floor for generic ONVIF Profile S cameras on a local gigabit LAN: 1–10 ms.** The lower bound (~1 ms) requires all cameras to sync to the same local NTP server and assumes reasonable firmware implementations. The upper bound (~10 ms) accounts for:
- Camera firmware using long poll intervals (64–1024 s).
- Lack of NTP kernel discipline on embedded Linux camera SoCs.
- Jitter from camera CPU load (video encoding, ONVIF stack).

### 2.2 NTP Sync Status Visibility
- **ONVIF does not expose** NTP client stratum, offset, jitter, or sync status through standard Device Management operations.
- Some vendors expose this via proprietary ONVIF extensions or through the camera's web UI (e.g., Axis VAPIX `getNTPInfo` returns `synced`, `timeOffset`, `timeToNextSync`).
- A generic ONVIF client **cannot** read NTP sync state portably.

### 2.3 Relationship to Adoption Threshold
NTP alone achieves ≤ 5 ms only under favorable conditions (dedicated local server, good firmware). The **1–10 ms range straddles the 5 ms threshold**, making NTP a marginal complement at best, and unreliable on cameras with poor NTP client implementations.

## 3. PTP Accuracy Evaluation

**Source:** Allied Vision Application Note "IEEE 1588 Precision Time Protocol with Prosilica GT, GC, Manta, and Mako G" — "PTP provides microsecond precision without increasing component cost ... software based master clock on a non real time operating system ... generated very poor synchronization plagued by significant jitter."
**Source:** Basler Product Documentation — "The precision of the PTP synchronization depends to a large extent on your network hardware and setup. For maximum precision, choose high-quality network hardware, use PTP-enabled network switches, and add an external PTP clock device with a GPS receiver."
**Source:** e-con Systems / Edge AI and Vision Alliance articles, 2023–2024.

### 3.1 Prevalence in Consumer/Prosumer Cameras
- **Rare / Uncommon.** PTP is primarily found in **industrial GigE Vision cameras** (Basler, FLIR/Point Grey, Allied Vision, e-con Systems) and some high-end broadcast cameras.
- Generic ONVIF Profile S IP security cameras (Hikvision, Dahua, Axis consumer lines, Reolink, etc.) **do not typically expose IEEE 1588 PTP**.
- PTP requires hardware timestamping support in the Ethernet PHY/MAC. Most camera SoCs used in budget/mid-range security cameras omit this.

### 3.2 Hardware vs. Software Timestamping
| Mode                                    | Typical Accuracy                      | Requirements                                             |
| --------------------------------------- | ------------------------------------- | -------------------------------------------------------- |
| Hardware timestamping (NIC PTP offload) | < 1 µs – 100 µs                       | PTP-capable PHY, boundary/transparent clocks on switches |
| Software timestamping (kernel `ptp4l`)    | 10–100 µs on RTOS; 1–10 ms on Windows | CPU load, interrupt latency, OS scheduling               |

### 3.3 Network Infrastructure Requirements
- **PTP Grandmaster** clock (preferably GPS-disciplined).
- **PTP-aware switches** (boundary clocks or transparent clocks) for multi-hop networks. Unmanaged switches introduce asymmetry that degrades accuracy.
- All cameras must support IEEE 1588-2008 (v2).

### 3.4 Camera-Generic Feasibility Assessment
**Infeasible for generic Profile S cameras.** PTP is not an ONVIF-managed service, support is hardware-dependent, and the target production cameras (per `07-CONTEXT.md` assumption A-05) are unlikely to support it. Even if supported, the infrastructure cost (grandmaster, managed switches) exceeds the value for a plugin targeting hands-off live production.

## 4. `GetSystemDateAndTime` Round-Trip Analysis

**Source:** NIST Technical Report "Practical Limitations of NTP Time Transfer" — Eq. (1) and (2) for clock offset from RTT.
**Source:** Stack Overflow / Network Engineering consensus on one-way latency estimation.

### 4.1 SOAP over HTTP RTT on LAN
- **Direct client-to-camera HTTP (same switch):** 0.2–2 ms RTT typical.
- **Single-hop gigabit LAN:** 1–5 ms RTT typical.
- **Congested or WiFi-linked LAN:** 5–20+ ms RTT.

### 4.2 Clock-Delta Estimation from RTT
The classical NTP offset formula applies:

```
offset = ((t2 - t1) + (t3 - t4)) / 2
delay  = (t4 - t1) - (t3 - t2)
```

Where:
- `t1` = client sends `GetSystemDateAndTime` request
- `t2` = camera receives request (unknown to client)
- `t3` = camera sends response (contains `UTCDateTime`)
- `t4` = client receives response

**Assumption:** The one-way delay is symmetric (request path delay ≈ response path delay).
**Reality:** Asymmetry from switch buffering, camera CPU scheduling, and IRQ coalescence introduces error. The error is bounded by the total asymmetry, which can be a large fraction of the RTT on embedded devices.

### 4.3 Jitter and Repeated Sampling
- A single `GetSystemDateAndTime` call yields one sample with uncertainty ≈ `RTT/2 ± asymmetry`.
- For a typical 2 ms RTT with 1 ms asymmetry, the instantaneous clock-delta error is ±1 ms.
- Camera firmware may take **tens to hundreds of milliseconds** to generate the SOAP response (XML serialization on a busy SoC), inflating RTT without corresponding network delay. This processing time is indistinguishable from network delay unless the camera timestamps `t2` and `t3` internally — which ONVIF does not require.

### 4.4 Achievable Accuracy
| Condition                                                         | Estimated Accuracy |
| ----------------------------------------------------------------- | ------------------ |
| Ideal: low RTT (< 1 ms), symmetric path, fast camera SOAP stack   | 0.5–2 ms           |
| Typical: 2–5 ms RTT, moderate asymmetry, consumer camera firmware | 2–8 ms             |
| Poor: WiFi, congested LAN, or slow camera CPU                     | 5–20 ms            |

### 4.5 ≤ 5 ms Achievable?
**Marginal.** Under ideal wired-LAN conditions with fast-responding cameras, yes. Under typical conditions with consumer/prosumer cameras, the accuracy floor is **2–8 ms**, which often exceeds the 5 ms threshold. The method is also statistically noisy — a single outlier RTT (e.g., camera busy with video encoding) can throw off the estimate by > 10 ms.

## 6. Integration Path Feasibility

**Source:** `src/av_sync_filter.c` — `av_sync_analysis_thread` (Phase 6 background pthread).
**Source:** `obsproject/obs-studio` — `rtmp-stream.c` / `rtmp-stream.h` (OBS output plugin threading model).
**Source:** OBS Studio Backend Design docs — libobs spawns dedicated audio, video, and graphics threads; plugins may spawn their own threads.

### 6.1 Path 1: Direct ONVIF from Plugin

- **OBS plugins can spawn background pthreads.** Confirmed by:
  - `av_sync_filter.c` creates `analysis_thread` via `pthread_create`.
  - OBS's own RTMP output plugin uses `connect_thread`, `send_thread`, and `socket_thread`.
- **Blocking TCP on a dedicated background thread is safe.** The critical rule (from Phase 3, `07-CONTEXT.md`) is: **no blocking or heap allocation on OBS audio callbacks.** A background thread doing `curl_easy_perform` or `send`/`recv` does not violate this.
- **OBS API restrictions:** There is no documented prohibition on outbound network I/O from plugins. OBS output plugins (RTMP, SRT, RIST) routinely open TCP/UDP sockets from plugin code. The only concern is ensuring the thread is properly joined in `destroy`.
- **XML/SOAP CPU cost:** Parsing a ~1 KB SOAP response on a background thread that wakes every 500 ms is negligible. The analysis thread already runs GCC-PHAT on 4-second windows; adding a SOAP parse is < 1% CPU overhead.
- **Thread lifecycle:** Follow the existing pattern: `pthread_create` in filter `create`, `pthread_join` in `destroy`, signal exit via an atomic bool.

### 6.2 Path 2: External Tool / Helper Process

- **Standalone utility:** A separate process queries cameras via ONVIF and writes clock-deltas to an IPC channel.
- **IPC options:**
| Option                   | Latency      | Complexity | Portability                                            |
| ------------------------ | ------------ | ---------- | ------------------------------------------------------ |
| File polling             | 100 ms – 1 s | Very low   | Universal, but high latency and filesystem wear        |
| Named pipe / FIFO        | < 1 ms       | Medium     | Windows (named pipes) vs. POSIX FIFO — APIs differ     |
| localhost UDP/TCP socket | < 1 ms       | Medium     | Universal, but port collision risk; firewall issues    |
| Shared memory            | < 1 ms       | High       | Platform-specific (POSIX shm vs. Windows file mapping) |
- **Operational complexity:** User must launch a second process, or the plugin must auto-launch it. Auto-launch requires process management (spawn, monitor, restart) that is non-trivial and error-prone.

### 6.3 Preferred Path

**Direct ONVIF from plugin (Path 1).**

**Rationale:** The plugin already manages a background analysis thread per filter. Adding ONVIF polling to that thread (or a secondary thread spawned by the filter/module) is a straightforward extension. It keeps the user experience single-process and avoids IPC latency and operational complexity.

### 6.4 Technical Blockers for External Path
- **IPC latency:** Even 1 ms of IPC latency is 20% of the 5 ms budget.
- **Process lifecycle management:** If the helper crashes or the user kills it, the plugin silently loses drift data. Detecting and recovering this is more code than direct integration.
- **Deployment:** Distributing a second executable complicates the CMake build and installer for all three platforms.
- **No clear benefit:** Direct network I/O from a background thread is already proven safe in OBS; externalizing it solves no problem.

## Summary of Key Findings (07-01)

| Mechanism                     | Accuracy Floor           | Feasibility | Verdict                                    |
| ----------------------------- | ------------------------ | ----------- | ------------------------------------------ |
| NTP (camera internal client)  | 1–10 ms typical          | Marginal    | **Marginal** — straddles 5 ms threshold        |
| PTP (IEEE 1588)               | < 1 µs – 1 ms (hardware) | Infeasible  | **Infeasible** — rare on generic ONVIF cameras |
| `GetSystemDateAndTime` SOAP RTT | 2–8 ms typical           | Marginal    | **Marginal** — noisy, asymmetry-sensitive      |
| **Combined best case**            | ~2–5 ms                  | Limited     | **Defer** — no clear path to reliable ≤ 5 ms   |

**Overall Recommendation:** **Defer** ONVIF clock sync for v1. The existing GCC-PHAT + EMA smoother (≤ 20 ms residual, < 1 ms synthetic) is more reliable and does not depend on camera firmware NTP quality or network asymmetry. Revisit ONVIF if:
1. OBS exposes Media Source timing metadata natively (eliminating need for ONVIF), or
2. The target camera fleet is upgraded to models with guaranteed PTP or sub-millisecond NTP discipline.

## 8. Media Source (RTMP) Timing Metadata

### 8.1 How `audio->timestamp` is generated for Media Sources

OBS Media Sources use the shared `media-playback` layer (`shared/media-playback/media-playback/media.c`). The critical path is `mp_media_next_audio`:

**Source:** `obsproject/obs-studio/shared/media-playback/media-playback/media.c:L341-L362`

```c
void mp_media_next_audio(mp_media_t *m)
{
    struct mp_decode *d = &m->a;
    struct obs_source_audio audio = {0};
    AVFrame *f = d->frame;

    if (!mp_media_can_play_frame(m, d))
        return;

    d->frame_ready = false;
    if (!m->a_cb)
        return;

    /* ... plane setup ... */

    audio.samples_per_sec = f->sample_rate * m->speed / 100;
    audio.speakers = convert_speaker_layout(f->ch_layout.nb_channels);
    audio.format = convert_sample_format(f->format);
    audio.frames = f->nb_samples;
    audio.timestamp = m->full_decode ? d->frame_pts
                     : m->base_ts + d->frame_pts - m->start_ts + m->play_sys_ts - base_sys_ts;

    if (audio.format == AUDIO_FORMAT_UNKNOWN)
        return;

    m->a_cb(m->opaque, &audio);
}
```

For normal (non-full-decode) playback, the timestamp is computed as:

```
timestamp = base_ts + frame_pts - start_ts + play_sys_ts - base_sys_ts
```

Where:
- `frame_pts` = FFmpeg decoded frame PTS (in stream timebase, converted to nanoseconds)
- `start_ts` = first PTS of the current playback segment
- `base_ts` = accumulated offset across loops/resets
- `play_sys_ts` = `os_gettime_ns()` when playback became active
- `base_sys_ts` = global static set once at module load to `os_gettime_ns()`

**Key finding:** The original container PTS is **rewritten into OBS's wall-clock domain**. The plugin layer never sees `frame_pts` directly.

### 8.2 Additional timestamp processing in `source_output_audio_data`

**Source:** `obsproject/obs-studio/libobs/obs-source.c` (audio output path)

After `media-playback` delivers the frame, `source_output_audio_data` further manipulates the timestamp:

```c
/* detects 'directly' set timestamps as long as they're within a certain threshold */
if (uint64_diff(in.timestamp, os_time) < MAX_TS_VAR) {
    source->timing_adjust = 0;
    source->timing_set = true;
    using_direct_ts = true;
}

if (!source->timing_set) {
    reset_audio_timing(source, in.timestamp, os_time);
} else if (source->next_audio_ts_min != 0) {
    diff = uint64_diff(source->next_audio_ts_min, in.timestamp);
    if (diff > MAX_TS_VAR && !using_direct_ts)
        handle_ts_jump(source, source->next_audio_ts_min, in.timestamp, diff, os_time);
    else if (diff < TS_SMOOTHING_THRESHOLD) {  /* 70 ms */
        if (source->async_unbuffered && source->async_decoupled)
            source->timing_adjust = os_time - in.timestamp;
        in.timestamp = source->next_audio_ts_min;
    }
}

in.timestamp += source->timing_adjust;
in.timestamp += sync_offset;        /* user/plugin sync offset */
in.timestamp -= source->resample_offset;
```

**Implications:**
- Timestamps are **smoothed** if they differ by < 70 ms from the expected cadence
- Large jumps (> 2 s, `MAX_TS_VAR`) trigger a **timing reset** that discards buffer state
- The `sync_offset` is baked into the mixing timestamp
- What the filter receives via `filter_audio` has already been through **two layers** of remapping

- Timestamp jumps
- Buffer underrun/overrun
- Network jitter
- Clock drift

**Plugin-visible?** Yes, via `obs_source_get_signal_handler`, but **not useful for drift tracking**.

### 9.3 Output Statistics (Plugin-visible, wrong layer)

`obs_output_get_frames_dropped`, `obs_output_get_total_frames`, and `obs_output_get_total_bytes` are public APIs, but they measure the **output encoding/streaming** layer. A plugin can call them, but they reveal nothing about per-source ingest timing or camera clock drift.

### 9.4 `obs_source_get_audio_mix` (Plugin-visible)

Returns the actual mixed audio buffers. While a plugin could theoretically analyze these buffers externally, the returned `obs_source_audio_mix` contains **no timing metadata** beyond what `obs_source_get_audio_timestamp` already provides.

## 10. OBS vs. ONVIF Timing Gap Analysis

| Timing Question                                               | OBS Can Answer                                                                    | ONVIF Can Answer                                                                                |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| What is the current per-source AV sync offset?                | **Yes** — `obs_source_get_sync_offset` returns the applied offset (user or plugin set). | **No** — ONVIF has no visibility into OBS pipeline state.                                           |
| What is the camera's current wall-clock time?                 | **No** — OBS never queries the camera's clock.                                        | **Yes** — `GetSystemDateAndTime` returns the camera's system time (subject to network RTT).           |
| What is the end-to-end ingest delay (network + decode)?       | **No** — No receive timestamp or latency API exists.                                  | **Partial** — Camera may report encoder delay, but the RTMP network path is opaque to ONVIF.        |
| Is the source experiencing clock drift relative to reference? | **No** — All timestamps are remapped to OBS's timeline; original PTS is discarded.    | **Yes** — If camera clock is queried and compared to a common NTP reference, drift can be detected. |
| What is the original stream PTS/timebase?                     | **No** — `audio->timestamp` is remapped to nanoseconds since `base_sys_ts`.               | **No** — ONVIF Device Management does not expose media-layer PTS.                                   |
| Is there network jitter on the RTMP ingest?                   | **No** — No jitter or buffer-depth statistics per source.                             | **No** — ONVIF operates over HTTP/SOAP, not the RTMP transport.                                     |
| Does the source have pending/unrendered audio?                | **Yes** — `obs_source_audio_pending`.                                                   | **No** — Not a camera-side concept.                                                                 |

### 10.1 Can clock deltas be inferred without ONVIF?

**No.** From the plugin layer, the following critical pieces of information are **unavailable**:

1. **Camera wall-clock time** — OBS has no protocol to query it.
2. **Original container PTS** — Rewritten in `mp_media_next_audio` before any filter sees it.
3. **Receive timestamp** — `av_read_frame` consumes packets but does not tag them with a wall-clock receive time accessible to plugins.
4. **Network jitter or buffer depth** — No API exposes RTMP ingest statistics per source.

The `audio->timestamp` field visible in `filter_audio` is an **OBS-internal mixing cursor**. Two cameras with identical content but different network delays will present **indistinguishable** timestamps to a filter, because OBS normalizes them into its own continuous timeline via `base_sys_ts`, `play_sys_ts`, and `timing_adjust`.

### 10.2 What ONVIF would actually add

ONVIF `GetSystemDateAndTime` would allow the plugin to know the **camera's clock**. If that clock drifts relative to the house reference (or a shared NTP server), the drift can be measured **independently of audio content**. However:

- ONVIF measures **camera clock drift**, not RTMP transport jitter.
- The RTMP proxy/ingest path introduces its own variable delay that ONVIF cannot observe.
- Achievable accuracy is bounded by network RTT (typically 1–10 ms over LAN).
- The camera must actually implement `GetSystemDateAndTime` accurately (some budget cameras return cached or imprecise values).

### 10.3 Relationship to GCC-PHAT

The existing GCC-PHAT + EMA smoother measures **end-to-end offset**, which implicitly includes:
- Camera clock drift
- Encoder buffering
- Network transport variation
- OBS ingest buffering

ONVIF would **not replace** GCC-PHAT. At best, it could provide an independent **camera-clock-drift** measurement that might help disambiguate whether observed long-term drift is due to:
- (A) Camera clock running fast/slow, or
- (B) Network path changing (e.g., RTMP proxy buffer growth).

Because GCC-PHAT already captures the total effect of (A) + (B), ONVIF is only valuable if knowing the camera clock separately enables a better correction strategy — e.g., predicting drift before it manifests in audio correlation.

### 10.4 Verdict for Plan 07-03

The gap that ONVIF would fill is **narrow**: it provides camera clock visibility that OBS entirely lacks, but it does not solve transport-layer jitter, and the existing GCC-PHAT engine already measures the composite result of clock drift + network variation. The decision in Plan 07-03 should weigh whether ≤ 5 ms camera-clock accuracy is achievable in practice and whether that knowledge improves the smoother beyond what audio correlation alone provides.
