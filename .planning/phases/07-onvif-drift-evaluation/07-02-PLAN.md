# Plan 07-02: Evaluate OBS Timing Metadata

## Objective
Investigate what OBS Studio exposes about RTMP/Media Source timing metadata through the `obs_source_t`, `obs_output`, and related APIs. Determine whether clock deltas are inferable from the plugin layer without a direct ONVIF connection. Output feeds into `07-RESEARCH.md`.

## Context & Decisions
| Decision | Rationale | Source |
|----------|-----------|--------|
| Investigate OBS timing APIs before committing to ONVIF | If OBS already exposes receive timestamps or PTS/DTS, ONVIF may be unnecessary | `07-CONTEXT.md` D-15, D-16 |
| Check `obs_source_get_sync_offset`, audio timestamps, output timing APIs | These are the documented touchpoints for per-source timing in OBS | `07-CONTEXT.md` D-16, `docs/ARCHITECTURE.md` |
| Document findings in `07-RESEARCH.md` §OBS Timing Exposure | Ensures all timing-related research is centralized for the recommendation doc | `07-CONTEXT.md` D-16 |

## Tasks

### Task 1: Survey OBS source timing API surface
<read_first>
- `.planning/phases/07-onvif-drift-evaluation/07-CONTEXT.md` (decisions D-15, D-16)
- `docs/ARCHITECTURE.md` (OBS API touchpoints table)
- `src/av_sync_filter.c` (current usage of `obs_source_get_sync_offset`, `audio->timestamp`)
</read_first>

<action>
Survey the OBS Studio public plugin API (libobs) for timing-related functions. Read OBS headers or online API docs (https://docs.obsproject.com/) and document the existence, signature, and purpose of each:

1. `obs_source_get_sync_offset` — documented behavior, return type, whether it returns the user-set offset or a measured offset
2. `obs_source_get_audio_timestamp` or `obs_source_get_timestamp` — if it exists, what it returns (frame PTS, wall clock, stream time)
3. `obs_source_get_timing` or similar timing metadata functions in `obs-source.h`
4. `obs_output` timing functions: `obs_output_get_total_bytes`, `obs_output_get_frames_dropped`, `obs_output_get_active_delay`, and any functions related to output timing or clock
5. `obs_source_get_frame_interval` or media-duration related functions
6. Whether `struct obs_source_info` or `struct obs_audio_data` contains any timing metadata beyond `timestamp`

For each function found, record:
- Header file and exact C signature
- What the documentation says it returns
- Whether it is applicable to Media Sources (RTMP ingest) or only to local sources

For each function NOT found, explicitly note "Not found in OBS public API" so the negative result is documented.
</action>

### Task 2: Investigate Media Source (RTMP ingest) timing metadata
<read_first>
- `.planning/phases/07-onvif-drift-evaluation/07-CONTEXT.md` (decisions D-15, D-16)
- `.planning/phases/07-onvif-drift-evaluation/07-RESEARCH.md` (after Task 1)
- `docs/ARCHITECTURE.md` (high-level design diagram and data flow invariants)
</read_first>

<action>
Investigate whether OBS Media Sources (FFmpeg-based RTMP ingest) expose any of the following to plugins:

1. **Receive timestamp** — Does OBS record the wall-clock time when an RTMP frame was received? Check FFmpeg source (`obs-ffmpeg-source.c` or equivalent) and OBS media source implementation for any receive-time logging or metadata.
2. **PTS/DTS** — Does the `obs_audio_data.timestamp` field correspond to presentation timestamp from the container, or is it rewritten by OBS? Check OBS source code or documentation for how timestamps are generated for Media Sources.
3. **Stream timebase** — Is there a way to query the original stream timebase (e.g., 1/90000 for MPEG-TS) from a Media Source?
4. **Frame delay / jitter stats** — Does OBS expose any statistics about network jitter or buffer depth for Media Sources?
5. **Decoder latency** — Is there any API to query how far behind "now" the decoded frame is?

Document the mechanism by which OBS generates `audio->timestamp` for Media Sources. If it is derived from the container PTS, note whether drift between container clock and OBS wall clock is observable.
</action>

- At least one concrete finding about PTS/DTS exposure is present
- A statement about whether receive timestamps are accessible is present (accessible / not accessible / unclear)
</acceptance_criteria>
